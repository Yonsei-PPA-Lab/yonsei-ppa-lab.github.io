4주차 제출물에는 어레이 아래로 나온 값을 4×4 결과 행렬에 저장하는 코드가 등장합니다. FSM의 각 상태에서 저장할 원소를 정한 코드도 있고, 별도 수확 모듈을 제출한 경우도 있습니다.

## 마지막 출력만 읽으면 놓치는 값

Weight-stationary 어레이에서 가중치는 PE 안에 머무릅니다. 입력과 부분합은 계속 이동하므로, 맨 아래 PE의 출력도 매 클럭 바뀔 수 있습니다. 완료 신호가 켜졌을 때 출력 네 개만 읽는 것으로는 결과 행렬의 원소 16개를 모두 모을 수 없습니다.

그래서 각 값이 유효한 클럭에 별도 결과 레지스터로 복사합니다. 여기서 수확(harvesting)은 새로운 곱셈을 하는 일이 아니라, 이미 계산된 값을 올바른 위치에 보존하는 일입니다.

## 결과는 대각선 순서로 모인다

입력 행을 한 클럭 간격으로 연속 공급하고 열별 출력도 한 클럭씩 엇갈리는 일정에서는 다음 순서로 결과를 저장할 수 있습니다. 아래의 `t0`는 **C[0][0]을 결과 레지스터에 저장하는 클럭**입니다.

| 저장 시점 | 저장할 원소 |
|---|---|
| t0 | C[0][0] |
| t0 + 1 | C[1][0], C[0][1] |
| t0 + 2 | C[2][0], C[1][1], C[0][2] |
| t0 + 3 | C[3][0], C[2][1], C[1][2], C[0][3] |
| t0 + 4 | C[3][1], C[2][2], C[1][3] |
| t0 + 5 | C[3][2], C[2][3] |
| t0 + 6 | C[3][3] |

첫 저장이 시작 신호로부터 몇 클럭 뒤인지는 가중치 로드, 입력 레지스터, PE의 파이프라인, 결과 저장 단계에 따라 달라집니다. 따라서 위 표의 상대적인 순서와 전체 실행 지연은 구분해야 합니다. 실제 제어기에 적용할 때는 해당 구현의 파형으로 `t0`를 확인합니다.

## 8비트 입력이면 부분합도 확인하기

4주차 코드에는 8비트 입력과 20비트 결과 배열을 사용하는 예가 있습니다. 입력 폭만 늘리고 곱셈 결과나 부분합을 좁게 두면, 마지막 결과 배열이 넓어도 앞에서 잘린 값을 복구할 수 없습니다.

예를 들어 부호 없는 8비트 값 네 쌍을 곱해서 더할 때 가능한 최댓값은 다음과 같습니다.

```text
4 × 255 × 255 = 260100
2^17 = 131072 < 260100 < 262144 = 2^18
```

이 입력 범위 전체를 지원하려면 최종 합에 18비트가 필요합니다. 입력이 signed인지 unsigned인지, 곱셈 결과가 어느 폭으로 계산되는지, PE 사이에서 어떤 폭으로 전달되는지까지 함께 확인해야 합니다.

## 파형에서 확인할 것

- 첫 유효 출력이 나온 클럭과 결과 레지스터에 저장된 클럭이 맞는가
- 원소 16개를 각각 한 번씩 올바른 행·열 위치에 저장하는가
- 다음 클럭에 어레이 출력이 바뀌어도 저장한 결과는 유지되는가
- 마지막 결과 저장과 완료 신호의 관계가 명확한가
- 최댓값에 가까운 입력이나 연속된 두 행렬에서도 이전 값이 섞이지 않는가

통과 여부는 같은 코드 버전으로 실행한 비교 결과와 로그를 근거로 판단합니다.
